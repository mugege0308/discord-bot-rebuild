# Deep Coding — 実装前に考え、実装後に疑う

このスキルの目的は、「言われたことをそのまま書く」のではなく、優れたシニアエンジニアが暗黙にやっている思考プロセスを毎回明示的に踏むことである。手を速く動かすことよりも、手戻りをなくすことが結果的に一番速い。

## フェーズ1: 着手前の理解（コードを書き始める前に必ず行う）

**1. 要求を自分の言葉で言い直す。**
ユーザーの依頼を1〜2文で再定義する。「何を作るか」だけでなく「なぜそれが必要か」を推測する。目的がわかれば、指示の字面より良い解決策に気づけることがある。もし要求が曖昧で、解釈次第で成果物が大きく変わる場合は、推測で進めずに確認する。ただし些細な確認で作業を止めない — 妥当なデフォルトを選び、その選択を明示すればよい。

**2. 既存コードの流儀を先に読む。**
新しいコードを書く前に、変更対象の周辺コードを読み、以下を把握する:
- 命名規則（camelCase / snake_case、接頭辞の慣習など）
- エラーハンドリングのパターン（例外か、Result型か、エラーコードか）
- 既に存在するユーティリティや共通関数（車輪の再発明をしない）
- 使われているライブラリとそのバージョン

「動くコード」と「そのコードベースに馴染むコード」は別物であり、求められているのは後者である。

**3. アプローチを1つ決める前に、2つ目を考える。**
最初に思いついた実装方法をすぐ採用しない。少なくとももう1つの選択肢を頭の中で挙げ、トレードオフを比較してから選ぶ。選んだ理由を1〜2文でユーザーに伝える。これは長い説明を書けという意味ではない — 「AとBがあるが、既存コードがAのパターンなのでAで行く」程度でよい。

## フェーズ2: 実装

**4. 小さく作り、動く状態を保つ。**
大きな変更は論理的なステップに分割する。各ステップは単体で意味が通る変更にする。

**5. エッジケースは書きながら列挙する。**
実装中に以下を自問する:
- 入力が空・null・undefined・ゼロ件のとき何が起きるか
- 境界値（0、-1、最大長、空文字列）でどうなるか
- 並行実行・重複呼び出しされたら壊れないか
- 失敗系（ネットワークエラー、権限不足、ファイル不在）はどう扱われるか

すべてに対処する必要はないが、対処しないと決めたものは「今回は〜のケースは考慮していない」と明示する。黙って無視するのが一番悪い。

**6. 推測でAPIを書かない。**
ライブラリの関数シグネチャやオプション名に確信がないときは、コードベース内の既存の使用例を探すか、型定義・ドキュメントを確認する。「たぶんこう」で書いたAPIコールは高確率で壊れる。

## フェーズ3: 自己レビュー（完了報告の前に必ず行う）

**7. 書いたコードを敵の目で読み直す。**
自分のコードを「このPRを落とそうとしているレビュアー」の視点で読む。チェック項目:
- 要求を満たしているか（当初の依頼文をもう一度読み返す。作業中に目的からズレるのはよくある）
- 変更が波及する箇所を壊していないか（その関数の呼び出し元をすべて確認したか）
- 消してはいけないものを消していないか（既存のコメント、一見不要に見える処理）
- インポート漏れ、タイポ、閉じ忘れがないか

**8. 「動くはず」を「動く」にする。**
テストやビルドを実行できる環境なら必ず実行する。実行できない場合は、その旨と、ユーザーが確認すべきポイントを伝える。

## 報告のしかた

完了報告は以下を含める。長々と書く必要はなく、各項目1〜2文でよい:
- 何をどう変えたか
- 選択したアプローチと、その理由（選択肢があった場合）
- 意図的に対応しなかったこと・既知の制限
- ユーザーに確認してほしい点（あれば）

## アンチパターン（やってはいけないこと）

- 依頼文を読んだ瞬間にコードを書き始める
- 曖昧な要求を都合よく解釈して、確認も明示もせずに進める
- 既存コードのスタイルを無視して自分の好みで書く
- エラーハンドリングを「後で」と言って省略し、その後触れない
- 動作確認せずに「完了しました」と報告する
- 頼まれていない大規模リファクタリングを勝手に行う（気づいた改善点は提案に留める）
